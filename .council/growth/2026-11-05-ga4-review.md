## Proposed product decision — not an installation instruction

Use a basic opt-in model: no Google tag, Google preconnect or Google measurement request before explicit acceptance. Rejection must be as easy as acceptance, and analytics must not be a condition of reading or using a calculator. No advertising consent or personalised advertising is part of this proposal.

Google distinguishes basic consent mode, which blocks tags until interaction and transfers no data when consent is not granted, from advanced mode, which can load tags and send cookieless pings before consent. Consent mode does not itself supply a consent banner. We propose the basic approach, not advanced pings. [Google: consent mode](https://support.google.com/analytics/answer/10000067), accessed 2026-11-05.

The eventual banner wording needs a completed data-flow and privacy review before it can truthfully describe the integration. Proposed copy for that review:

> Optional analytics helps us understand which pages readers use. If you accept, we would use Google Analytics to estimate visits and improve the site. We would not send calculator answers or form text. You can reject analytics and keep using the site, or change your choice later.

Proposed equal-weight actions: **Accept analytics** / **Reject analytics**. Proposed persistent entry point: **Analytics choices**. Proposed withdrawal action: **Turn off analytics**. Avoid “anonymous”, “all bots removed”, “exact people”, “GDPR compliant” or “no personal data” claims. These are drafts, not live statements or a claim about what a future SDK automatically collects.

## Consent state contract

| Review state | Proposed measurement commands | Review-kit behaviour | Future implementation that is still required |
| --- | --- | --- | --- |
| Undecided | None | Analytics denied; no commands | Prevent loader, requests and identifier writes before a choice; keep core content available. |
| Rejected | None | Analytics denied; no commands | Persist an agreed rejection without analytics; do not replace it with repeated prompts on each page. |
| Accepted, valid example | Sanitised config plus one manual `page_view` data example | Still uninstalled; no request or choice stored | Load only after acceptance; prove one view per intended navigation and sanitise every emitted payload. |
| Accepted, invalid ID or page | None | Generic reason code, no raw input echoed | Fail closed; never fall back to an unsanitised browser URL. |
| Withdrawn | None | New proposal has no commands | Block further collection, handle the already-loaded SDK and remove applicable analytics identifiers across their domains/paths; persist the changed choice. Test immediately and on reload/navigation. |

The planner deliberately has no stateful SDK, storage or cookie deletion code. Showing “withdrawn” is **not** proof that a real SDK has stopped or its cookies have been removed. A deployed change-of-mind route, browser evidence and reviewed deletion/retention behaviour remain activation gates.

## Payload boundary chosen for this proposal

This finite demonstration allowlist covers the homepage, Card Finder, comparison page, Salary Tracker, its calculator, Skywards and the eligibility guide. Other routes are refused; expansion requires review of the public route inventory, not a permissive catch-all.

The planner accepts canonical HTTPS DubaiPoints URLs or root-relative allowlisted paths, reconstructs them from a fixed origin and strips **every** query and fragment. It refuses external origins, embedded credentials, ambiguous/encoded paths and internal routes. It never includes input URLs in errors. `page_referrer` is explicitly blank and `page_title` is the fixed text `DubaiPoints`: this initial proposal sacrifices acquisition detail to minimise exposure.

There are no arbitrary event names or additional parameters. No form text, search text, salary, spend, email, user identifier, advertising click ID or free-form title/referrer can be added through the planner input. No application, bank approval, commission, purchase or revenue event is planned. Fixed fictional salary/email/advertising query examples test removal only; they are not collected.

The data example uses `send_page_view: false`, a separate manual sanitised `page_view`, `allow_google_signals: false` and `allow_ad_personalization_signals: false`. Proposed consent metadata keeps `ad_storage`, `ad_user_data` and `ad_personalization` denied. Google's configuration reference documents the page URL/referrer/title overrides and these configuration switches; an explicit empty referrer avoids relying on its automatic default. These are proposed settings, not evidence of a functioning consent barrier. [Google: GA4 configuration reference](https://developers.google.com/analytics/devguides/collection/ga4/reference/config), accessed 2026-11-05.

Google's data-redaction feature is best effort and does not evaluate the HTTP referrer header; it is not the primary control here. [Google: data redaction](https://support.google.com/analytics/answer/13544947), accessed 2026-11-05. Before activation, inspect real request headers and all SDK-generated/automatic events as well as our manually supplied parameters. Disable enhanced-measurement options initially; do not assume the helper controls every automatic field. Browser metadata, identifiers, destination processing, transfers and onward use need a complete actual-integration inventory.

Google offers standard GA4 retention choices of 2 or 14 months for the covered user/event data. Its retention setting does not govern standard aggregated reports in the same way it governs explorations/funnels; reset-on-new-activity can extend user-identifier retention. These distinctions must be captured when approving the purpose, not reduced to “everything is deleted after two months”. [Google: data retention](https://support.google.com/analytics/answer/7667196), accessed 2026-11-05.

## What the monthly visitors report could and could not mean

Use an explicit label: **GA4 Total users, consented production traffic, calendar month in Asia/Dubai; known bots excluded by GA4 to the extent possible**. Show coverage start date and the last complete month separately from a partial current month. Leave numbers unavailable until measured; no historical estimate is produced by this kit.

Google defines Total users as unique users who triggered any event in the selected period; Active users meet engagement-related criteria. These are different measures. [Google: user metrics](https://support.google.com/analytics/answer/12253918), accessed 2026-11-05. For DubaiPoints reporting, neither should be relabelled as a verified count of natural people: a person may use several devices/browsers or reset an identifier, and non-consenting readers are absent from this proposed opt-in collection.

- Report a whole-month Total users metric, not the sum of daily, per-device or per-page unique counts. A reader may appear in multiple rows/days.
- Page views are repeated page loads/views, not distinct visitors; sessions are not natural people either. Do not reconcile Cloudflare visits and GA4 users as if they were identical measures.
- GA4 cannot backfill a period in which it collected nothing. Rejected, blocked and pre-acceptance activity would not become measured retrospectively under this proposal.
- Consented coverage is incomplete and may be biased. Do not scale it to “all visitors” without a justified method; identify report scope and uncertainties.
- Google's known-bot/spider exclusion is automatic to the extent possible, not proof that all bots have been removed, and the excluded amount is not shown. [Google: exclude known bots](https://support.google.com/analytics/answer/9888366), accessed 2026-11-05. Mostafa's standing “exclude bots” requirement remains the objective; reports must state the attainable filter and residual uncertainty.
- Improvements can be investigated through sanitised page popularity and device/landing-page patterns once collection is approved and sufficiently representative. No visitor count, low view count or apparent drop-off alone proves a design cause.

## Activation gates — every item remains open

1. Mostafa reviews the scope, metric label and all account/privacy/retention/filter choices above. Confirm which existing Cloudflare reports remain the baseline.
2. Obtain the actual account/property/stream information through an authorised private route; assess the Google terms, actual data flow, applicable privacy obligations and consent/notice wording. This plan does not assert a legal basis or jurisdictional compliance.
3. Implement a separate production consent controller, persistent choices and accessible change-of-mind UI. Store only the agreed choice data with an approved duration; no analytics identifiers before opt-in. Do not reuse this demonstration as that controller.
4. Review every route, URL source, event, SDK default, header, storage operation and cookie scope. Disable enhanced measurement/Ads/signals and unapproved integrations; prove no raw calculator parameters, form values, search text or identity can leave.
5. Test a fresh browser, undecided, rejection, acceptance, withdrawal, reload, navigation, expired choice, blocked scripts, keyboard and no-script behaviour. Capture network/storage evidence on desktop and physical iPhone Safari. In this kit, the test remains “no integration exists”, not “real withdrawal certified”.
6. Test traffic filters before enabling permanent exclusions; review access and reporting configuration with the owner. Establish the first collection date and a complete-month reporting template with coverage notes.
7. Obtain the required Council/Chairman sign-off and explicit owner authority for activation in a separate change. Make only the agreed production integration, then independently verify it live and record the effective date. No new tag, property, analytics destination or paid service is authorised by the present review.
